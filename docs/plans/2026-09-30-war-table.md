## Outcome and bounded design

The Questmancer can see prerequisites, affected work and ownership in one selected
campaign, then read the exact quest, request and artifact evidence. The current
alternative is opening each quest in the Board and reading its dependencies.
A campaign graph should reduce that effort; five-second comprehension remains
an unmeasured human target. The main usability risk is an attractive graph hiding
facts when the campaign or viewport grows.

Use a contextual RGB War Table over the existing Hall/Delve, with static cards,
prerequisite-to-dependent links, source lifecycle cues and a separate human-request
marker. Reuse the existing roster tool/check cues and parchment palette. Full
literal titles and facts remain readable in the selected parchment; shortened
card labels show an explicit continuation marker. Never shrink adventurer art.

`w` opens/closes the Table. `j/k` cycle quests; Tab/Shift-Tab cycle campaigns;
Up/Down or wheel reads selected details; `b` opens the selected quest's Board;
Enter observes only an M1-verified binding; `!` uses the unchanged attention queue.
The Table can be opened from the Board. Existing counsel drafts remain intact.
No source answer, assignment, dependency activation or local seen/defer write is
performed by Table navigation.

Dependency layout is deterministic by typed identity. Missing and outside-campaign
prerequisites are attributed in details. Cycles are diagnosed; they never imply
readiness. If a complete DAG fits, render all its nodes and links. Otherwise show
a labelled, selection-following inventory map; the details retain prerequisites
and dependents, including those outside the visible page. Narrow panes use the
selected-work parchment and explicit map-unavailable cue. Empty campaigns and
missing source state remain truthful. No graph animation or decorative wakeups.

The appetite is one fixture-backed implementation slice using existing primitives,
not a general graph editor. If a whole graph does not fit, use the honest fallback;
do not add zoom, physics, drag, a second renderer or orchestrator semantics.

## Implementation and gates

1. Red test: auth dependencies become explicit directed edges; human request
   remains separate from Active lifecycle, and projection does not mutate work.
2. Pure campaign graph projection, deterministic DAG layers and cycle diagnostics.
   Keep this distinct from the live-only SceneSnapshot and persisted work facts.
3. Ephemeral campaign/quest navigation and input integration. Normalise selection
   after source changes; no cross-source identity guessing or persistence effects.
4. RGB table/cards/links through `render_scene_for_world`; contextual text overlay
   reuses production details/wrapping. Small/large/cyclic fallbacks retain access.
5. Feature-gated fixed Storybook scenarios: populated, narrow, empty, offline,
   cyclic and large inventory. All use fixture sources and production render paths.
6. Regression tests for source isolation, dependencies/cycles/missing references,
   navigation/selection removal, obligation/defer distinction, artifact freshness,
   fixed-input render determinism, reduced/still motion and positive small sizes.
7. Run focused tests, affected scene/input/interaction/Storybook suites, `just verify`,
   release build and diff checks. Retain exact dirty-tree receipt and production
   cell exports. Obtain production visual approval; native terminal acceptance
   remains independent. No five-second comprehension claim from test timings.
